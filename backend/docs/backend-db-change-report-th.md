# รายงานการปรับปรุงระบบ Backend และฐานข้อมูล KU Marketplace

วันที่จัดทำ: 9 กันยายน 2026  
ฐานเปรียบเทียบ: `origin/backend/main` ที่ commit `91b6f12`  
สาขาที่ทำงาน: `develop` ที่ HEAD `4f7d40f` รวมการเปลี่ยนแปลงใน working tree ณ วันที่จัดทำ

## 1. วัตถุประสงค์และขอบเขต

งานนี้มีวัตถุประสงค์เพื่อตรวจสอบและแก้ไขปัญหาการทำงานของ backend และฐานข้อมูล ให้ผู้พัฒนารายอื่นสามารถติดตั้งและทดลองระบบได้สะดวกขึ้น รวมถึงลดความผิดพลาดด้านสิทธิ์ผู้ใช้ การเปลี่ยนสถานะธุรกรรม และความถูกต้องของข้อมูลเมื่อมีคำขอเข้ามาพร้อมกัน

การตรวจสอบอ้างอิงทั้ง flow ด้านบนและด้านล่างของ [Activity Diagram](../../frontend/docs/activity%20diagram.pdf) ครอบคลุมการซื้อขาย แลกเปลี่ยน แจกสินค้า นัดหมาย ยกเลิก คืนเงิน คืนสินค้า รายงาน และอุทธรณ์ ส่วนระบบยืนยันตัวตนและสมาชิกเป็นขอบเขตเพิ่มเติมของแอปพลิเคชัน

เอกสารนี้แยกงานที่มีอยู่ก่อนแล้วออกจากงานแก้ไขรอบนี้ เพื่อไม่ให้รายงานความเปลี่ยนแปลงจากหลายสาขารวมเป็นผลงานรอบเดียว

## 2. ความสัมพันธ์ระหว่างสาขา

หลังอัปเดตข้อมูล remote ด้วย `git fetch origin` พบว่า `origin/backend/main` มี commit ล่าสุดคือ `91b6f12` ลงวันที่ 27 สิงหาคม 2026 และเป็นบรรพบุรุษของ `develop` ปัจจุบัน กล่าวคือ `develop` รวมประวัติของสาขานี้ไว้แล้ว

ผล `git rev-list --left-right --count origin/backend/main...HEAD` เป็น `0 207` หมายถึงไม่มี commit ฝั่ง `backend/main` ที่ขาดจาก HEAD ปัจจุบัน และมีอีก 207 commits ฝั่ง `develop` ตัวเลขนี้นับทั้งโครงการ ไม่ใช่เฉพาะ backend

| --- | --- | --- |
| ฐาน backend หลัก | `origin/backend/main` | Commit `91b6f12` |

ยังมี `origin/feature/init-database` ซึ่งมีงานข้อมูลตัวอย่างใหม่กว่า `backend/main` และถูกรวมเข้า `develop` แล้ว ดังนั้นการใช้ `backend/main` เพียงสาขาเดียวเป็นฐานเปรียบเทียบ จะเห็นงานเก่าจากสาขาอื่นรวมอยู่ด้วย

## 4. การเปลี่ยนแปลงฐานข้อมูลรอบนี้

### 4.1 ตารางและคอลัมน์ที่เกี่ยวข้อง

| ตาราง/คอลัมน์ | การเปลี่ยนแปลง | เหตุผล |
| --- | --- | --- |
| `Item.quantity` | เติมใน `init.sql` และ migration เป็น `INTEGER NOT NULL DEFAULT 1` | ให้ฐานข้อมูลใหม่และฐานข้อมูลเดิมรองรับฟิลด์ที่ Prisma ใช้อยู่ |
| `Item.deleted_at` | เติมใน SQL และ migration | รองรับการลบแบบเก็บแถวข้อมูลไว้สำหรับประวัติและหลักฐาน |
| `Post.deleted_at` | เติมใน SQL และ migration | รองรับ soft delete ของประกาศให้ตรงกับ Prisma |
| `Transaction.refund_submitted_at` | เพิ่ม `TIMESTAMP` ที่เป็น NULL ได้ และ map เป็น `refundSubmittedAt` ใน Prisma | เริ่มนับกำหนดยืนยันคืนเงินจากเวลาส่งสลิปจริง |
| `Report.sanction` | เพิ่ม `VARCHAR(30)` ที่เป็น NULL ได้ | บันทึกโทษของแต่ละคำตัดสิน เพื่อแยกผลของการอุทธรณ์แต่ละเรื่อง |
| `Notification` | เพิ่มตารางใหม่และ relation กับผู้ใช้ | เก็บการแจ้งเตือนในแอปอย่างถาวรและป้องกันแจ้งเตือนซ้ำ |

`deletedAt` ของ Item และ Post มีอยู่ใน Prisma ของ `backend/main` แล้ว การเปลี่ยนส่วนนี้จึงเป็นการทำ SQL ให้ตรงกับ model ที่ใช้งาน ไม่ใช่การสร้างแนวคิด soft delete ขึ้นใหม่ทั้งระบบ

สำหรับ `Item.quantity` นั้น `init.sql` ของฐานข้อมูลใหม่มี `CHECK (quantity > 0)` ส่วน migration ที่ใช้เพิ่มคอลัมน์ให้ฐานข้อมูลเดิมไม่ได้เพิ่ม CHECK ดังกล่าว การตรวจจำนวนที่ API จึงยังมีความสำคัญ และไม่ควรระบุว่า constraint ของทั้งสองเส้นทางเหมือนกันทุกประการ

### 4.2 โครงสร้าง Notification

| คอลัมน์ | ประเภท/ข้อกำหนด | หน้าที่ |
| --- | --- | --- |
| `notification_id` | SERIAL, primary key | รหัสการแจ้งเตือน |
| `user_id` | INTEGER, foreign key ไป `User.user_id` | ผู้รับการแจ้งเตือน |
| `event_key` | VARCHAR(255), UNIQUE | ระบุเหตุการณ์เพื่อป้องกันการสร้างซ้ำ |
| `title` | TEXT, NOT NULL | หัวข้อ |
| `body` | TEXT, NOT NULL | ข้อความ |
| `href` | TEXT, NOT NULL | เส้นทางหน้าที่เกี่ยวข้อง |
| `created_at` | TIMESTAMP, default CURRENT_TIMESTAMP | เวลาสร้าง |

เพิ่ม index บน `(user_id, created_at)` เพื่อรองรับการดึงรายการของผู้ใช้ตามเวลา ระบบนี้เป็นการแจ้งเตือนภายในแอป ไม่ใช่การส่งอีเมลหรือ push notification ไปยังอุปกรณ์ และยังไม่มีคอลัมน์สำหรับบันทึกว่าอ่านแล้ว

## 5. การปรับปรุง Backend

### 5.1 การยืนยันตัวตนและการตรวจข้อมูล

- ผูก `ZodValidationPipe` กับ Auth และ Membership และใช้ `ClassValidatorPipe` กับ Items ให้ตรงกับชนิด DTO ของแต่ละ controller
- ป้องกันการส่ง `ownerId` หรือสถานะสินค้าเพื่อเปลี่ยนค่าที่ผู้ใช้ไม่ควรแก้ได้โดยตรง
- อ่านตัวตนผู้ซื้อและผู้เสนอแลกจากผู้ใช้ที่ผ่านการยืนยันตัวตน แทนการเชื่อรหัสผู้ใช้ที่ส่งมาใน body
- ใช้ Redis Lua script เปรียบเทียบและใช้ OTP ภายในคำสั่งแบบ atomic ทำให้คำขอยืนยันพร้อมกันไม่สามารถใช้ OTP เดียวสำเร็จสองครั้ง
- สร้างข้อมูลผู้ใช้และสมาชิก Free เริ่มต้นร่วมกันใน nested write ของ Prisma
- ตรวจสถานะบัญชีและสิทธิ์แอดมินจากฐานข้อมูลใน JWT guard เพื่อให้ token เก่าไม่ข้ามการระงับบัญชีได้
- อนุญาตบัญชี Suspended/Banned ให้เข้าดูโปรไฟล์และใช้งานอุทธรณ์ที่กำหนดไว้ แต่ยังปิดการซื้อขาย การแก้สินค้า และงานแอดมิน บัญชี Deleted ใช้งานต่อไม่ได้

ไฟล์หลัก: [AuthService](../src/auth/auth.service.ts), [OtpService](../src/auth/otp.service.ts), [JwtAuthGuard](../src/auth/guards/jwt-auth.guard.ts)

### 5.2 สินค้า ประกาศ และข้อเสนอแลกเปลี่ยน

- ตรวจเจ้าของก่อนแก้ไขประกาศหรือดำเนินการแทนผู้ขาย
- ตรวจราคาและจำนวนให้เป็นค่าที่ใช้ได้ และไม่ลงประกาศเกินจำนวนสินค้า
- ใช้ transaction, row lock และ conditional update ในจุดสำคัญ เพื่อไม่ให้ผู้ซื้อสองคนจองหน่วยสุดท้ายสำเร็จพร้อมกัน
- ตรวจและล็อกของที่ใช้เสนอแลก เพื่อไม่ให้ของชิ้นเดียวถูกยอมรับในสองธุรกรรม
- รองรับการนำประกาศที่ soft delete แล้วกลับมาใช้ โดยเก็บรหัสแถวเดิม พร้อมข้อจำกัดสำหรับประกาศที่มีรายงานและสินค้าที่ถูกจอง
- ป้องกันการลบสินค้าที่ประกาศอยู่หรือผูกกับธุรกรรม และป้องกันการเปลี่ยนจำนวนที่กระทบการจอง
- เมื่อขายเพียงบางส่วน สินค้าที่มีสต็อกประกาศเหลือยังเป็น Listed

ไฟล์หลัก: [PostsService](../src/posts/posts.service.ts), [ItemsService](../src/items/items.service.ts)

### 5.3 ธุรกรรม การยกเลิก และการคืนสินค้า

ปรับ state transition ให้รองรับ `Pending Refund` และ `Refunded` ใน service และ enum ของแอปพลิเคชัน สองค่านี้มีอยู่ในข้อกำหนดสถานะของฐานข้อมูลเดิมแล้ว จึงไม่ใช่การเพิ่มสถานะ DB ใหม่ในรอบนี้

| เหตุการณ์ | พฤติกรรมที่ปรับปรุง |
| --- | --- |
| ส่งสลิปชำระเงิน | เปลี่ยน Pending เป็น Processing เมื่อสถานะปัจจุบันยังอนุญาต |
| คำขอส่งสลิปล่าช้ากว่าการยกเลิก | ปฏิเสธคำขอเก่า ไม่ทำให้รายการ Cancelled กลับมาดำเนินต่อ |
| ยกเลิกก่อนชำระเงิน | คืนการจองสต็อกเพียงครั้งเดียว แม้มีคำขอพร้อมกัน |
| ยกเลิกหลังชำระเงิน | ผ่านการตอบรับและขั้นตอนคืนเงินก่อนปิดผลการคืนเงิน |
| คืนสินค้าหลังรายการสำเร็จ | ตรวจช่วงเวลาคืนภายใน 7 วัน และเงื่อนไขตอบรับ |
| ต้องคืนทั้งเงินและของ | บันทึกทั้งสองเงื่อนไข และปิดเป็น Refunded เมื่อครบสิ่งที่ต้องคืน |
| แลกโดยไม่เพิ่มเงิน | ส่งมอบและคืนของได้โดยไม่ต้องสร้างหลักฐานชำระเงินที่ไม่มีจริง |
| QR คืนสินค้า | แยก token จาก QR ส่งมอบเดิม และตรวจบทบาทผู้แสดง/ผู้สแกน |

แพลตฟอร์มบันทึกหลักฐานและการยืนยันจากคู่กรณี ไม่ได้ดำเนินการโอนเงินผ่านธนาคารให้ผู้ใช้

### 5.6 รายงานและอุทธรณ์

ตรวจว่าผู้รายงานธุรกรรมเป็นคู่กรณีจริงและเป้าหมายมีอยู่ บันทึกโทษแยกต่อรายงาน เมื่ออนุมัติอุทธรณ์จะพิจารณาโทษจากรายงานอื่นที่ยังมีผล ไม่เปลี่ยนบัญชีกลับเป็น Active โดยไม่ตรวจสอบ

กรณีข้อมูลคำตัดสินเก่าที่ไม่มีค่า `sanction` ระบบไม่สามารถอนุมานโทษเดิมได้อย่างแน่นอน หากมีคำตัดสินที่ยังมีผลและไม่ทราบโทษ จะคงการระงับเดิมไว้ นอกจากนี้เพิ่มการดึงรายการคำตัดสินที่ผู้ใช้มีสิทธิ์อุทธรณ์ โดยไม่ส่งหลักฐานส่วนตัวทั้งหมดให้ผู้ร้องอุทธรณ์

ไฟล์หลัก: [ReportService](../src/report/report.service.ts), [AppealService](../src/report/appeal.service.ts)

### 5.7 สมาชิกและโควตาโพสต์

ใช้ row lock และ database transaction ป้องกันคำขอสมัครซ้ำและการตัดสินสลิปพร้อมกันจนสถานะการชำระกับระดับสมาชิกขัดแย้งกัน บังคับโควตาขณะสร้างประกาศจริง โดยนับประกาศที่สร้างในเดือนปฏิทิน UTC รวมประกาศที่ถูกลบแล้ว แทนการอาศัยตัวนับสะสมที่อาจไม่ตรงกับข้อมูลจริง

โควตาที่ใช้ตามค่ากำหนดเดิม: Free 3, Silver 10, Gold 25 และ Diamond ไม่จำกัด งานนี้บังคับใช้ค่าที่มีอยู่ ไม่ได้เปลี่ยนราคาหรือโควตาของแพ็กเกจ

### 5.9 การติดตั้งและ API ที่เกี่ยวข้อง

- เปลี่ยนพอร์ต backend เริ่มต้นจาก 3000 เป็น 4000 เพื่อไม่ชนกับ frontend
- เพิ่ม `postinstall: prisma generate` และคำสั่ง `prisma:generate`

## 6. การอัปเดตฐานข้อมูลที่ใช้งานในเครื่อง

ก่อนเปิดเซิร์ฟเวอร์ ตรวจพบว่า DB ในเครื่องมีคอลัมน์จำนวนสินค้าและ soft delete อยู่แล้ว แต่ยังไม่มี `refund_submitted_at`, `Report.sanction` และตาราง Notification

จึงสำรองฐานข้อมูลด้วย `pg_dump` แล้วรันเฉพาะ migration `20260909010000_flow_notifications` และ `20260909020000_report_sanction` ไม่ได้รัน seed ใหม่ ไม่ได้ล้าง volume และไม่ได้เปลี่ยนรหัสผ่านบัญชีเดิม ไฟล์สำรองในเครื่องอยู่ที่ `/tmp/ku-start-backup/before-start.dump` ซึ่งเป็นพื้นที่ชั่วคราว ไม่ใช่ไฟล์ที่รวมไปกับ repository

การเปิด backend ทำให้งานตามกำหนดเวลาเริ่มตรวจข้อมูลที่ถึงกำหนดตามปกติ ผลจาก scheduler ต้องแยกจากการเปลี่ยน schema ด้วย migration

สำหรับเครื่องอื่น ให้ใช้ขั้นตอน [Existing databases ใน README](../../README.md#existing-databases) เพราะสภาพ schema อาจต่างจากเครื่องที่ตรวจ ไม่ควรถือว่าทุกเครื่องต้องรันเพียงสอง migration เดียวกัน

## 8. ข้อจำกัดและข้อพิจารณา

ผลทดสอบข้างต้นไม่ใช่การรับรองว่าไม่มีบัคในทุกเส้นทาง ยังไม่ได้ยืนยันกล้องโทรศัพท์จริง การอัปโหลดและส่งอีเมลผ่านบัญชีบริการภายนอกทุกกรณี การกู้คืนหลังบริการขัดข้องทุกแบบ และทุกเงื่อนไขขอบเขตเวลาจากทั้งสอง diagram

สำหรับ QR ต้องแยกหลักฐานให้ชัด: การส่งมอบแบบ meetup มีการทดสอบ Redis จริง ส่วนบางเคส QR คืนสินค้ายังใช้ตัวแทน Redis ในชุดทดสอบ

มีจุดขัดกันใน diagram เรื่องสถานะสินค้าหลังยกเลิกก่อนส่งมอบ งานนี้ใช้การคืนการจองและความพร้อมขาย เนื่องจากสินค้ายังไม่ได้เปลี่ยนมือ โดยบันทึกไว้ใน [Combined activity diagram audit](../../frontend/docs/design/activity-diagram-audit.md) จึงควรอธิบายว่าเป็นการตีความจุดขัดกัน ไม่ใช่ทำตรงกับข้อความทั้งสองแบบพร้อมกัน

## 9. ตัวอย่างข้อความสำหรับนำไปเรียบเรียงในรายงาน

> การปรับปรุงระบบ Backend และฐานข้อมูลของ KU Marketplace ดำเนินการบนสาขา develop ซึ่งรวมประวัติจากสาขา backend/main แล้ว โดยตรวจสอบความสอดคล้องกับ Activity Diagram ทั้งสองชุด งานหลักประกอบด้วยการแก้ความไม่สอดคล้องระหว่าง Prisma model และ SQL initialization การเพิ่มข้อมูลกำหนดเวลาคืนเงิน การจัดเก็บการแจ้งเตือน และการบันทึกโทษแยกตามรายงาน นอกจากนี้ได้ปรับการตรวจสิทธิ์ผู้ใช้และการเปลี่ยนสถานะธุรกรรม พร้อมใช้ database transaction, row locking, conditional update และคำสั่ง Redis แบบ atomic ในจุดที่อาจเกิดคำขอพร้อมกัน เพื่อรักษาความถูกต้องของสต็อกและป้องกันการดำเนินการซ้ำ ผลทดสอบ backend ประกอบด้วย unit tests 20 เคสและ integration tests 26 เคสที่ผ่านการตรวจสอบ รวมถึงการอัปเกรดฐานข้อมูลเดิมโดยคงข้อมูลเดิมไว้ ทั้งนี้ยังมีการทดสอบอุปกรณ์จริงและบริการภายนอกที่ต้องดำเนินการเพิ่มเติมก่อนรับรองการใช้งานครบทุกเส้นทาง
